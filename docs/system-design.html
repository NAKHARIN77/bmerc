1. ภาพรวมและคำศัพท์

ระบบมีผู้ใช้ 2 ชั้น ชั้นบนคือ เจ้าของแพลตฟอร์ม (เรา) ที่ขายแพ็กเกจให้ บริษัทศูนย์ซ่อม ชั้นล่างคือพนักงานในแต่ละบริษัทที่ใช้ระบบรับเครื่องจากลูกค้า ซ่อม ตัดอะไหล่ และติด QR

คำในโค้ดความหมาย
บริษัทCompanyศูนย์ซ่อมที่สมัครใช้ระบบ (tenant) ข้อมูลของแต่ละบริษัทแยกขาดจากกัน

3. การแยกข้อมูลแต่ละบริษัท

ทุกบริษัทใช้ฐานข้อมูลเดียวกัน แต่ทุกตารางที่เป็นข้อมูลของบริษัทต้องมีคอลัมน์ company_id และป้องกันข้อมูลรั่วข้ามบริษัทไว้ 2 ชั้น:

  1. ชั้นแอป: ดึง company_id จาก JWT เท่านั้น ห้ามรับจาก body หรือ query แล้ว Prisma extension จะเติม where company_id = ? ให้ทุก query อัตโนมัติ
  2. ชั้นฐานข้อมูล: เปิด PostgreSQL Row-Level Security ทุกตาราง โดยตั้งค่า SET LOCAL app.company_id ในแต่ละ transaction ถ้าโค้ดลืมกรองข้อมูล DB จะไม่คืนข้อมูลบริษัทอื่นให้
เจ้าของแพลตฟอร์มดูข้อมูลบริษัทอื่นได้แค่แบบอ่านอย่างเดียว และเห็นทุกอย่างยกเว้นงานซ่อม (ใบงาน, timeline, เครื่องที่รับเข้า, อะไหล่ที่ใช้ในงาน, ใบแจ้งหนี้และการชำระค่าซ่อม) ข้อนี้บังคับด้วย RLS ตัวเลขสรุปของงาน เช่น จำนวนงานต่อบริษัท ต้องดึงผ่านฟังก์ชันเฉพาะที่คืนแต่ตัวเลข และทุกครั้งที่เข้าดูต้องลง audit log เพื่อให้เป็นไปตาม PDPA ส่วนหน้าภาพรวมให้ใช้ตัวเลขสรุป ไม่แสดงข้อมูลรายคน

ขอบเขตข้อมูลที่แต่ละบทบาทเห็น

RLS จำกัดข้อมูลให้อยู่ในบริษัทเดียว แล้ว API กรองต่อตามบทบาท (apps/api/src/auth/scope.ts) ทุก query ของบริษัทต้องใช้ตัวกรองนี้

  • แอดมินบริษัท: ทุกไซต์ในบริษัท
  • ผู้จัดการไซต์, คนคุมสต็อก: เฉพาะไซต์ใน user_sites คนคุมสต็อกเห็นสต็อกและงานซ่อม (เพื่อเบิกอะไหล่เข้างาน) เฉพาะไซต์ที่ดูแล แต่เห็นแคตตาล็อกอะไหล่ทั้งบริษัท และไม่สังกัดทีม
  • หัวหน้าช่าง, ช่าง: เฉพาะไซต์ของทีมตัวเอง และเห็นเฉพาะงานที่ยังไม่มีคนรับ หรืองานที่คนในทีมเดียวกันรับไว้ ช่างที่ยังไม่มีทีมจะไม่เห็นงานเลย

เปิดงานที่อยู่นอกขอบเขตจะได้ 404 ไม่ใช่ 403 เพื่อไม่บอกว่างานนั้นมีอยู่ เปลี่ยนบทบาท ทีม หรือไซต์แล้วมีผลทันทีในคำขอถัดไป เพราะระบบอ่านสิทธิ์จากฐานข้อมูลทุกครั้ง ไม่ได้เก็บไว้ใน token

เชิญผู้ใช้และลืมรหัสผ่าน

  • แอดมินบริษัทสร้างผู้ใช้โดยยังไม่มีรหัสผ่าน ระบบส่งลิงก์เชิญอายุ 7 วัน ผู้ใช้ตั้งรหัสผ่านเองแล้วเข้าระบบทันที ถ้ายังไม่กดลิงก์จะล็อกอินไม่ได้
  • ลิงก์รีเซ็ตรหัสผ่านอายุ 1 ชั่วโมง ทุกลิงก์ใช้ได้ครั้งเดียว ขอลิงก์ใหม่แล้วลิงก์เก่าใช้ไม่ได้ เก็บเฉพาะ hash ในตาราง user_tokens
  • forgot-password ตอบ 204 เสมอ ไม่บอกว่ามีอีเมลนี้ในระบบหรือไม่ และจำกัดได้ 3 ครั้งต่อ 15 นาทีต่ออีเมล
  • ตั้งหรือรีเซ็ตรหัสผ่าน และปิดบัญชี จะทำให้ทุก session เดิมหลุด
  • เชิญหรือเปิดบัญชีคืน ต้องไม่เกินจำนวนผู้ใช้ของแพ็กเกจ (max_users หรือ override_limits.maxUsers) นับรวมคนที่ยังไม่รับคำเชิญ
  • บริษัทต้องมีแอดมินที่ใช้งานอยู่อย่างน้อย 1 คน และแอดมินเปลี่ยนบทบาทตัวเองหรือปิดบัญชีตัวเองไม่ได้
  • ยังไม่ได้ต่อผู้ให้บริการส่งอีเมล ตอนนี้ MailService เขียนอีเมลลง log ไว้ก่อน ต้องเลือกผู้ให้บริการก่อนขึ้นระบบจริง

แพ็กเกจ Basic มีผู้ใช้ได้ 1 บัญชีที่เป็นแอดมินบริษัท บทบาทหัวหน้าช่าง ช่าง และคนคุมสต็อก ใช้ได้เฉพาะแพ็กเกจ Pro ตามหน้า Pricing ในต้นแบบ

6. สถานะงานซ่อม

ขั้นตอนจริง: ลูกค้าส่งเครื่องหรือบอร์ดมาที่ศูนย์เอง (ไม่มีการออกไปซ่อมหน้างาน) → พนักงานเปิดใบงาน ค้นจาก serial ก่อนว่าเครื่องนี้เคยซ่อมมาหรือไม่ และบันทึกอาการเสีย → มอบหมายงานให้ช่างที่ไซต์ที่รับเครื่องไว้ → ช่างซ่อมตามสถานะด้านล่าง → ส่งคืนลูกค้า

ใช้ 5 คอลัมน์ตามบอร์ดในต้นแบบ แล้วเพิ่มอีก 2 สถานะท้ายสุดสำหรับส่งคืนลูกค้า ห้ามแก้ status ตรง ๆ ทุกครั้งที่เปลี่ยนสถานะต้องผ่าน service และบันทึกลง job_events

7. กฎของระบบ

สต็อกอะไหล่

  • การเบิก รับเข้า และปรับยอด ต้องทำใน transaction เดียวกัน 3 ขั้น: SELECT … FOR UPDATE แถว site_stock, เขียน stock_movements แล้วอัปเดตยอด ป้องกันช่าง 2 คนเบิกพร้อมกันจนสต็อกติดลบ
  • ถ้าเบิกเกินยอดคงเหลือ ให้ปฏิเสธพร้อมข้อความว่าเหลือเท่าไร
  • การปรับยอดต้องระบุเหตุผล (ตามหน้า Adjust stock)
  • ถ้ายอดต่ำกว่า min_qty ให้แสดงสถานะ Low บนแดชบอร์ด ถ้าเหลือ 0 ให้แสดง Out และแจ้งเตือนคนคุมสต็อก
  • เมื่อยกเลิกการใช้อะไหล่ในงาน ให้สร้าง movement ย้อนกลับ ห้ามลบรายการเดิม

โควตาและแพ็กเกจ

  • นับใบงานที่เปิดในเดือนปฏิทินนั้นตาม timezone ของบริษัท
  • เมื่อใช้ถึง 80% ให้ขึ้นแถบเตือนในแอปและส่งอีเมลถึงแอดมิน 1 ครั้งต่อเดือน
  • เมื่อใช้ถึง 100% จะเปิดใบงานใหม่ไม่ได้ แต่งานที่เปิดไว้แล้วทำต่อได้ตามปกติ (ดู Q3)
  • จำนวนไซต์และผู้ใช้ถูกตรวจตอนสร้างใหม่ ใช้ค่าจาก override_limits ก่อน ถ้าไม่มีให้ใช้ค่าจาก plan

การชำระเงินและการระงับบริษัท

  • ออกใบแจ้งหนี้วันที่ 1 ของเดือน กำหนดชำระภายใน 7 วัน (ตามหน้า Payment details)
  • เมื่อเกินกำหนด สถานะจะเป็น past_due และขึ้นแถบเตือน ถ้าเกินกำหนดไปอีก 7 วันจะเป็น suspended
  • บริษัทที่ถูกระงับยังล็อกอินได้ แต่เห็นได้แค่หน้า "Account suspended" กับหน้าชำระเงิน ข้อมูลไม่ถูกลบ
  • เจ้าของแพลตฟอร์มกด Suspend หรือ Activate เองได้ และทุกครั้งต้องลง audit log

QR และประวัติเครื่อง

ลูกค้าส่งได้ทั้งเครื่องทั้งตัวและบอร์ดเดี่ยว ตอนรับของต้องเลือกประเภท (ทั้งเครื่อง / hashboard / control board / PSU / อื่น ๆ) เวลาซ่อมเครื่องทั้งตัวแล้วซ่อมหรือเปลี่ยนบอร์ด ให้บันทึก serial ของบอร์ดใน job_components (ถ้าเปลี่ยนบอร์ด ให้บันทึก serial ของบอร์ดใหม่ด้วย) ตอนค้นประวัติด้วย serial ต้องค้นทั้ง devices.serial_no และ serial ใน job_components ถ้าบอร์ดเคยซ่อมตอนอยู่ในเครื่อง แล้วภายหลังลูกค้าส่งมาเดี่ยว ๆ จะได้เห็นประวัติเดิม

  • รหัส QR สุ่มแบบเดาไม่ได้ เช่น BMERC-7K3QX9MD ไม่ใช้เลขเรียง เพื่อไม่ให้คนอื่นไล่เดาดูข้อมูลได้
  • สร้างรหัสครั้งเดียวต่อเครื่อง เมื่องานแรกของเครื่องผ่าน QC งานถัดไปใช้รหัสเดิม
  • เมื่อสแกน QR ต้องล็อกอินและอยู่บริษัทเดียวกันถึงจะเห็นประวัติ

Audit log

ต้องบันทึกอย่างน้อยเหตุการณ์เหล่านี้: ล็อกอินสำเร็จหรือล้มเหลว, เปลี่ยนสถานะงาน, มอบหมายงาน, ทุก movement ของสต็อก, เปลี่ยนสิทธิ์ผู้ใช้, เปลี่ยนแพ็กเกจหรือโควตา, Suspend/Activate และการที่เจ้าของแพลตฟอร์มเข้าดูข้อมูลบริษัท

การเปิดดูข้อมูลสำคัญบันทึกเป็น view.<entity> ด้วย decorator @LogView ตอนนี้ใช้กับรายละเอียดงานซ่อม (มีข้อมูลติดต่อลูกค้า), รายชื่อพนักงาน และ audit log เอง endpoint ใหม่ที่แสดงข้อมูลลูกค้า ใบแจ้งหนี้ หรือการชำระเงิน ต้องใส่ decorator นี้ด้วย

11. เรื่องที่ต้องตัดสินใจ

เจอข้อขัดกันหรือข้อที่ยังไม่ชัดในต้นแบบ ต้องตัดสินใจก่อนเริ่มสัปดาห์ 2

  1. ราคาแพ็กเกจ: หน้า Landing แสดง Pro ฿299/เดือน หน้า Pricing ยังเป็น [Price] ส่วนหน้า Revenue ตั้ง Basic ไว้ ฿1,500 ซึ่งแพงกว่า Pro ราคาจริงคือเท่าไร และราคารวม VAT หรือยัง?
  2. โควตาเต็ม: เมื่อ Basic เปิดใบงานครบ 200 ใบ จะปิดไม่ให้เปิดเพิ่ม หรือให้เปิดต่อได้แล้วคิดเงินส่วนเกิน?
  3. ภาษาหน้าจอ: ตัดสินแล้ว (22 พ.ย. 2026) เว็บใช้ภาษาอังกฤษทั้งหมด ต้นแบบมีฉบับเดียวคือภาษาอังกฤษ (เลิกใช้ฉบับไทยแล้ว 23 พ.ย. 2026)
  4. Hosting: ทีมมี cloud ที่ใช้อยู่แล้วไหม (AWS, GCP, DigitalOcean)? ถ้ามีลูกค้าไทยเป็นหลัก แนะนำ region สิงคโปร์
  5. ใบกำกับภาษี: บริษัทผู้ให้บริการจด VAT แล้วหรือยัง? ข้อนี้มีผลกับรูปแบบใบแจ้งหนี้และใบเสร็จ
  6. ใบเสนอราคาก่อนซ่อม: ต้องให้ลูกค้าอนุมัติราคาก่อนเริ่มซ่อมหรือไม่? ถ้าต้อง เสนอให้บังคับเฉพาะงานที่ค่าซ่อมเกินเกณฑ์ที่บริษัทตั้งไว้ (ยังไม่มีใน schema)

  • ลูกค้า: ไม่มีบัญชีและเข้าเว็บไม่ได้ ผู้ใช้ระบบมีแค่เจ้าของระบบ และพนักงานของบริษัท (แอดมิน ผู้จัดการไซต์ หัวหน้าช่าง ช่าง คนคุมสต็อก)
  • ผู้จัดการ: ใช้บทบาท site_manager เห็นเฉพาะไซต์ที่ผูกใน user_sites คนเดียวดูแลได้หลายไซต์
  • คนคุมสต็อก: ผูกกับไซต์แบบเดียวกับผู้จัดการไซต์ เลือกได้ 1 ไซต์หรือหลายไซต์ รับเข้า เบิก และปรับยอดได้เฉพาะไซต์ที่ดูแล การโอนระหว่างไซต์ให้ต้นทางบันทึกโอนออก แล้วปลายทางกดรับของ แจ้งเตือนของใกล้หมดส่งให้คนคุมสต็อกของไซต์นั้นและแอดมิน
  • ค่าซ่อม: ใช้ตาราง job_invoices, job_invoice_lines และ job_payments แยกจากใบแจ้งหนี้ค่าแพ็กเกจ
